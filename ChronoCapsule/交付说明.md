# ChronoCapsule 端侧交付说明

> 给队友（云端 / 集成）看的：怎么装、怎么接、现在的行为边界在哪。
> 端侧负责：无障碍自动抓屏 → 端侧 OCR → 结构化 → 跨屏去重 → 按契约 v0.4 上传 → 建任务取卡片。
> 云端负责：`POST /api/screens` 的接收、入库、Super-Agent 逻辑、卡片渲染数据。

---

## 1. 当前状态

| 能力 | 状态 |
| --- | --- |
| 手动：选图 / 示例图 → OCR → 结构化 → 契约自检 → 上传 → 建任务 → 显示卡片 | ✅ 模拟器 + 真机（release 包）全链路验证 |
| 自动：切到微信/QQ 自动抓屏 → 流水线 → 去重 → 上传 → 建任务 → 卡片 | ✅ 模拟器 + 真机（Android 16，微信/QQ 实聊）验证 |
| 跨屏去重（只传新增消息） | ✅ 单测 13 个 + 模拟器验证 |
| 去重历史落盘（进程被杀后仍有效） | ✅ 单测 + 模拟器验证（强杀进程后重启，整屏 4 条全部跳过） |
| 网络不可达时离线缓存 + 联网后补传 | ✅ 单测 6 个 + 模拟器验证（端口断开 → 缓存 1 屏 → 地址改对 → 补传成功） |
| 云端地址可配置 + 一键测连通 | ✅ 模拟器 + 真机验证（HTTP 200） |
| 非聊天页面过滤（网页 / 相册 / 公众号） | ✅ 真机验证（公众号文章被跳过，聊天页正常抓） |
| Release 签名构建 | ✅ 已签名的 APK 可直接安装 |

**没验证过的**：群聊昵称识别、深色模式、QQ 不同版本的活动类名差异（非聊天页过滤是按类名关键词挡的，新版本可能多出没见过的类名）。

## 2. 运行环境

- Android 11+（`minSdk 30`，`targetSdk 37`）
- ABI：`arm64-v8a`（真机）、`x86_64`（模拟器）——ONNX Runtime 只提供这两个
- 端侧模型：PP-OCRv6 tiny（det 1.7MB + rec 4.3MB），随 APK 打包，不需要联网下载
- 打包体积约 60MB，大头是 ONNX Runtime 的两个 ABI 原生库

## 3. 安装

### 方式一：直接装已签名 APK（推荐给演示）

```bash
adb install -r app/build/outputs/apk/release/app-release.apk
```

换手机/换签名时先卸载：`adb uninstall com.chronocapsule`

### 方式二：本地构建

Android Studio 直接打开工程即可；命令行需要一个 JDK 17：

```bash
# Windows，用 Android Studio 自带的 JBR
JAVA_HOME="D:/Android/Android Studio/jbr" ./gradlew.bat assembleDebug
JAVA_HOME="D:/Android/Android Studio/jbr" ./gradlew.bat assembleRelease
```

离线构建（没有代理时）加 `--offline`。跑单测：

```bash
JAVA_HOME="D:/Android/Android Studio/jbr" ./gradlew.bat --offline testDebugUnitTest
```

**签名**：`keystore.properties` + `chronocapsule-release.jks`（项目根目录，比赛演示用密钥）。
这两个文件不在你本地时，release 会**自动退回 debug 签名**，照样能构建、能装，只是不能覆盖安装我发的包。

> 别把 `keystore.properties` / `*.jks` 推到公开仓库，已在 `.gitignore` 里排除。

## 4. 首次使用的四步

1. **开启自动记录**：打开 App → 点「开启自动记录（无障碍）」→ 在系统「无障碍」里找到 ChronoCapsule 并打开。
   开启后按钮会变成「自动记录：已开启」（这个状态读的是系统设置，不是内存标志位）。
2. **填云端地址**：页面上那行输入框，比如 `http://192.168.1.5:8765`（真机连电脑时填电脑的局域网 IP；
   模拟器用 `adb reverse tcp:8765 tcp:8765` 后填 `http://127.0.0.1:8765`）。
3. **点「测试连接」**：走 `GET /api/screens`，成功会提示 `连接成功（HTTP 200，云端已有 N 屏）`。
4. **手动验一遍**：点「示例图」→「上传云端」，几秒后状态区上方出现云端卡片（或提示已生成），
   说明「上传 → 建任务 → 取卡片」整条链路都通。

## 5. 接口契约（v0.4）

端侧只调四个接口（上传两屏 + 建任务/取卡片两个）：

### `POST /api/screens`

```json
{
  "event_id": "evt-<uuid>",
  "session_id": "sess-<uuid>",
  "app_package": "com.tencent.mm",
  "app_name": "微信",
  "page_title": "张三",
  "captured_at": "2026-11-10T09:47:08.191495Z",
  "blocks": [
    {
      "id": "bubble-1",
      "kind": "chat",
      "speaker": "张三",
      "text": "今晚八点开会，记得带电脑",
      "message_at": "2026-11-10T20:32:00+08:00",
      "bbox": [122.9, 320.4, 143.8, 340.0]
    }
  ]
}
```

端侧发出去之前会本地自检一遍这些硬约束（和服务端 `extra="forbid"` 对齐）：

- 顶层**只能有这 7 个字段**，多一个就 422
- `blocks` ≥ 1 且 ≤ 60；单块 ≤ 4000 字；整屏 ≤ 24000 字
- `id` 只允许 `[a-zA-Z0-9_.:-]`，屏内唯一（去重后会从 `bubble-1` 连续重编）
- `captured_at` / `message_at` **必须带时区**
- `bbox` 为 `[x1, y1, x2, y2]`，已归一化到 0–1000，保证 `x1 ≤ x2`、`y1 ≤ y2`

字段映射规则：

| 字段 | 端侧怎么来的 |
| --- | --- |
| `app_package` / `app_name` | 无障碍服务拿到的真实前台包名；手动上传时为 `unknown` |
| `page_title` | 聊天页顶部标题（群名 / 对方昵称） |
| `speaker` | 自己说的记 `我`；单聊对端记标题；群聊记 OCR 到的昵称，认不出记 `对方` |
| `message_at` | 屏幕上的「20:32」按截图日期补全；只有月日用截图年份，补出未来日期算去年；**跨零点会记错一天** |
| `bbox` | 像素框按截图的宽高归一化 |

成功响应按 `{"screen": {"id": ...}, "replayed": false}` 解析；错误码语义：`409`（同 `event_id` 内容不同）、`422`（Schema 不满足）、`401/403`（鉴权）。

**幂等**：离线补传时会复用原来的 `event_id`，服务端可以放心按 `event_id` 去重。

### `GET /api/screens`

只用来做「测试连接」：返回 2xx 即视为通，并从 `{"screens": [...]}` 里读已有屏数展示给用户。
如果这个列表接口的形状变了，只影响提示文案，不影响上传。

> 鉴权目前**没接**：`CloudClient` 支持 `Authorization: Bearer <token>`，但 UI 没有填 token 的地方。
> 云端如果要加鉴权，把 token 存进 `CloudConfig` 就行，是十几行的改动。

### `POST /api/tasks` → `GET /api/tasks/{tid}`

上传的屏在云端只是「材料」，要拿到卡片必须再建一个任务。端侧在**每次上传成功之后**自动做这一步：

```json
POST /api/tasks
{
  "event_id": "task-<screen_id>",          // 固定拼法，同屏重复提交由云端幂等去重
  "instruction": "整理这一屏聊天里提到的时间、地点、待办和需要我回复的事项。",
  "screen_ids": ["scr_..."],               // 本次新上传的屏，1–20 个
  "interaction_protocol": "legacy"
}
```

服务端返回 `202 {"task": {"id": "task_...", "status": "queued", ...}, "replayed": false}`。
随后端侧每 1.5 秒 `GET /api/tasks/{tid}`，直到 `card` 非空（任务状态变为 `waiting_input`），
超时 90 秒（手动上传是 60 秒）；`failed` / `cancelled` 直接放弃，不影响已经上传的屏。

卡片只取这三个字段展示，完整结构原样保留在云端：

```json
{"title": "...", "summary": "...", "fields": [{"label": "...", "value": "..."}]}
```

自动记录拿到卡片后会发一条 App 内广播（`com.chronocapsule.CARD_READY`，只发本应用），
界面开着就能在状态区上方看到卡片；没开界面就只写日志（`ChronoCard`）。

**离线补传的屏不会再建任务**：`PendingUploads.drain()` 只补传材料，任务链只跟「刚刚这一屏」。
联调如果需要补传后也出卡片，在 `drain()` 拿到 `screen_id` 后调同一个 `CloudClient.analyzeScreen()` 即可。

## 6. 自动记录的行为（联调时按这个预期看数据）

- **只监听** `com.tencent.mm`（微信）、`com.tencent.mobileqq`（QQ）。
  加别的聊天 App 只需要在 `ScreenWatcherService.CHAT_PACKAGES` 里加一行。
- **触发**：`TYPE_WINDOW_STATE_CHANGED`（窗口切换）后等 350ms 再抓，避开切换动画。
- **只抓聊天页**：同一个 App 里微信的网页、图片查看器、公众号文章（Flutter 页面），
  QQ 的相册 / 空间 / 支付页也会发同样的窗口事件，按类名挡掉（`BLOCKED_WINDOW_CLASSES`）。
  真机实测不过滤的话，一屏相册能出 60 个垃圾块，还会把网页内容当成聊天上传。
- **限频**：两次抓图至少隔 1.5 秒；一分钟最多 20 张；上一张没处理完时只保留最新一屏，处理完补抓；
  卡住超过 20 秒强制复位。
- **息屏 / 锁屏**不抓。
- **输入法弹出时不抓**。输入法窗口事件会顶掉聊天 App 的事件，用「最近一次聊天 App」去猜键盘底下是谁，
  实测会把键盘按键一起 OCR 进来（整屏 36 条里 35 条是 Gboard 的键），所以宁可不抓。
  副作用：键盘弹着的时候不会触发新的采集。
- **跨屏去重**：按「会话（包名 + 页面标题）+ 说话人 + 文本」算指纹，每条消息带计数，
  只上传计数增加的部分。整屏都是旧消息时直接跳过上传（日志：`没有新消息…跳过上传`）。
  - 页面标题为空（认不出会话）时**不做去重**，宁多勿漏。
  - 内存里保留最近 32 个会话 × 每个 1024 条指纹；每屏处理完立刻写 `files/dedupe_history.txt`，进程被杀也能接着去重。
- **离线缓存**：连不上云端（`httpCode == -1`）时把整屏 JSON 落盘到 `files/upload_queue/`，
  最多 20 屏（超了丢最旧的）；服务启动时、以及下一次上传成功后自动补传。
  服务端已经答复的错误（4xx/5xx）**不重试**，直接丢弃——那是契约问题，重发也没用。

## 7. 排障

```bash
# 全链路日志
adb logcat -s ScreenWatcher:* ChronoPayload:* CloudClient:* PendingUploads:*

# 国产 ROM（iQOO / vivo 等）常把第三方应用的 logcat 对 shell 屏蔽，
# 这时读落盘的事件追踪（debug 包装了才取得到）：
adb shell run-as com.chronocapsule cat files/event_trace.txt
```

事件追踪只记事件类型、包名、类名、抓屏决策和上传结果，不记聊天原文；每个窗口事件一行，
排查「事件有没有来、为什么没抓、有没有传上去」够用。

| 现象 | 先看这里 |
| --- | --- |
| 切到微信没反应 | 日志里有没有 `窗口事件：…`。没有就是无障碍没真正生效：关掉再开一次（`adb install -r` 之后系统偶尔会留下「已启用但不投递事件」的状态） |
| 有事件但没抓图 | `上一张还在处理` / `息屏或锁屏` / `一分钟内已抓 N 张` |
| 抓了但不上传 | `没有识别出文字` / `没有新消息…跳过上传` / `自动上传：...` |
| 上传失败 | `CloudClient` 的 `POST ... → 500`；网络不通会进离线队列，日志里能看到 `已缓存` |
| 云端 422 | 先跑一遍 App 里的「示例图」，契约自检通过才有必要怀疑云端 |

注意：`adb shell am force-stop com.chronocapsule` 会把无障碍服务从系统启用列表里摘掉，
测完要重新去设置里开一次。

## 8. 已知限制 / 下一步

1. **真机上没跑过**微信 / QQ。最可能出问题的地方：某些机型聊天页复用同一个 Activity，
   切换会话不产生窗口事件（模拟器的短信 App 就是这样），那种情况下要加滚动 / 内容变化事件做兜底。
2. **新消息停留期间不会自己抓**：只在窗口切换时采集。用户一直停在同一个聊天页里，
   新到的消息要等下一次切换才会被记录。
3. **深色模式、大字体**未专门适配，OCR 结果可能偏差。
4. **跨零点**的消息会被记到前一天（`message_at`）。
5. **群聊昵称**靠 OCR 左侧昵称行，短昵称/头像附近文字容易串行。
6. **鉴权未接**（见第 5 节）。
7. `assets/models` 里还留着 PP-OCRv4 的两个模型（约 15MB）用于后续 A/B 对比，代码没有引用，
   要缩包可以直接删。

## 9. 关键文件

| 文件 | 作用 |
| --- | --- |
| `capture/ScreenWatcherService.kt` | 自动抓屏：窗口事件、限频、流水线、去重、上传 |
| `pipeline/ScreenPipeline.kt` | 一屏的完整处理流程（OCR → 结构化 → 契约） |
| `ocr/` | PP-OCRv6 tiny 的检测 / 识别（ONNX Runtime） |
| `struct/ScreenStructurer.kt` | 文字行 → 消息（谁说的、时间、气泡框） |
| `contract/ScreenContract.kt` | 契约 v0.4 的映射、自检、`renumber`、JSON 还原 |
| `dedup/CrossScreenDeduper.kt` | 跨屏去重 + 历史落盘 |
| `net/CloudClient.kt` | 上传 / 测试连接（`HttpURLConnection`，无第三方依赖） |
| `net/CloudConfig.kt` | 云端地址的存取与归一化 |
| `net/UploadQueue.kt` / `PendingUploads.kt` | 离线队列的存取与补传 |
| `MainActivity.kt` + `res/layout/activity_main.xml` | 手动上传、自动记录开关、云端地址、测试连接 |
