所有实验使用合成材料。真实模型是 deepseek-flash。测试使用独立数据库。

| 验收 | 观察结果 |
|---|---|

### 同一条变化的三组对照

三组共享同一份确认状态、原始材料和模型，场景为“小王可能迟到但确定参加，小林确定退出且蛋糕未订，固定套餐仍为 688 元”。五项检查是确定人数、退出的人、估算人均费用、职责缺口、是否引用退出的原文 ID。云端另检查正式版本未被候选覆盖。两组云端共用同一条提示，并要求在工具可用时先尝试审阅。本次每组仅运行一次，耗时包含本地框架和模型响应，不包括手机操作。主模型轮数按框架事件计，HTTP 重试次数和三组完整 token 成本未采集。

| 方案 | 检查通过 | 用时 | 模型与审阅 |
|---|---:|---:|---|
| 独立助手 | 5/5 | 9.33 秒 | 1 次，输入 1041 token、输出 994 token |
| 云端，关闭审阅 | 5/5 | 6.80 秒 | 主模型 2 轮，正式版本保持 v1 |
| 云端，提供审阅工具 | 5/5 | 43.70 秒 | 主模型 3 轮，辅助审阅失败，正式版本保持 v1 |

三组都答对了这一个场景。第三组观察到一次辅助审阅失败后的恢复，没有可据此宣称的准确率增益或延迟优势。下一轮可加入真实噪声、否定、多来源冲突和无答案材料，再决定哪些情况值得启用审阅。

从 `Cloud Agent` 目录复现。在本机通过现有环境配置选择真实模型，以下两条 `--run` 命令会调用模型。

```powershell
python -m pytest -q
python scripts/live-model-smoke.py --run --db artifacts/party-new-run.db --output artifacts/party-new-run.json
python scripts/compare-party-review.py --run --output artifacts/party-review-new-run.json
```

## 第二个插件复用了什么

| 能力 | Party | Schedule | 共有实现 |
|---|---|---|---|
| 业务变化 | 退出、分摊、职责与完成状态 | 改期、前置依赖、完成标记 | 事项关联、来源引用和历史回查 |
| 用户决定 | 确认交接或完成候选 | 澄清调整时间、确认改期 | `cloud-v1` 交互、恢复原任务、版本校验和提交 |
| 行动 | 由组织者核对交接记录 | 可单独授权导出 ICS | 业务插件提交候选，框架处理用户响应 |

实现位置见 [Party](../screenmind/agents/party.py)、[Schedule](../screenmind/agents/schedule.py)、[Worker](../screenmind/worker.py)、[存储与事务](../screenmind/store.py)及[共用交互协议](api-contract.md)。云端 Schedule 已验证合成通知的真实模型改期和澄清。用户日历实际导入、第二插件接入工时仍待核查。
