# SubAgent 扩展契约 v0.2

v0.4 增量：`Proposal` 可返回 `question`，由 Worker 发布 cloud-v1 澄清；`auxiliary_tools=("time_check",)` 声明辅助能力白名单；可选 `calendar_item(state, item_id)` 提供动作条目读取能力。Schedule 是第二个持续事项插件。外部动作仍由框架 ActionService 独立授权执行，插件不直接执行。详见 [v0.4](phase-two.md)。

v0.3 保留本插件接口；Worker 会将基础 MemoryProvider 返回的同事项历史加入 read_screens 结果与引用白名单。cloud-v1 模式额外提供框架级 ask_clarification 工具，插件不直接写正式状态或执行外部动作。协议说明见 [第一阶段实现](phase-one.md)。

框架共享 Router、任务执行器、队列、生命周期、版本校验、事项记忆、模型适配器和 HTTP/卡片协议。领域插件负责提示词、输出 Schema、业务规则、候选记忆及可选模拟流程。

`work_id` 标识一个持续事项，例如某一次生日聚会；`task_id` 标识一次处理，例如根据退出消息调整方案；`subagent_id` 标识可复用的能力，例如 `party`。一个事项有多次任务，一个能力服务多个事项。记忆不保存在 SubAgent 实例中。

## 新能力的最小实现

1. 在 `screenmind/agents/` 新增插件，实现 `base.SubAgent` 协议。
2. 提供唯一 `id`、名称、说明、匹配关键词、`requires_work`、`system_prompt`、`output_tool` 和 Pydantic 导出的 `output_schema`。
3. `propose(arguments, context)` 校验领域参数，返回 `Proposal(card, memory)`。`memory` 是待确认的完整 JSON 状态；返回 `None` 表示不更新记忆。
4. 如果希望无密钥演示，实现 `mock_reply(messages)`。真实 Provider 使用插件的提示词和工具 Schema，不调用 mock 逻辑。
5. 在 `agents.Registry` 的默认构造列表注册，或通过 `create_app(registry=Registry([...]))` 注入。无需修改 Router、Worker、Store 或 API。

插件是服务端受信任代码，不是安全沙箱。插件实例跨任务复用，必须无可变业务状态；每次执行都只使用传入的 `AgentContext`，不能把其他任务的上下文存进实例。当前上下文提供当前任务、其执行开始时的记忆快照及允许引用的来源，不提供任意数据库读取接口。

示例：`InformationAgent` 展示原文卡片；`PartyAgent` 展示领域 Schema、人数/费用计算、责任缺口和候选状态。测试 `test_extension_registered_without_runtime_changes` 通过注入第三个能力验证扩展接口。

## 当前工具边界

每个 SubAgent 通过通用 `read_screens` 读取当前任务的屏幕、当前事项的记忆快照和带引用的用户补充。之后调用自己注册的输出工具（例如 `present_party`）。当前版本支持“读取上下文 → 模型提出结构化状态 → 领域计算 → 候选卡片”这一类能力，没有任意网络或外部写入工具。

`propose` 是同步短计算，不应执行阻塞网络操作。以后接入地图、搜索或预订时，需要在框架增加有权限、超时和幂等约束的异步工具接口；不要在领域规则中暗藏外部副作用。

## 事项记忆

SQLite 的 `works` 保存当前已确认状态，`memories` 保存不可变版本历史。逻辑隔离键为 `owner + work_id`，不是每个事项创建一个物理数据库，也不是向量检索库。

- 任务取得执行槽时读取记忆，存为 `memory_snapshot` 与 `memory_base`。
- 插件输出存为任务的 `memory_proposal`；卡片出现不等于记忆生效。
- `confirm` 在一个事务内校验任务 revision、卡片版本及当前 memory_version，写入记忆、历史和事件，再结束任务。
- 记忆已被其他任务更新时返回 409。通过 revise 重新生成时读取新快照，再进行确认。
- cancel、failed 和失效轮次都不能修改已确认记忆。重启会保留事项与历史。
- 同一屏幕第一次绑定事项后不能用于其他事项；已用于旧版独立任务的屏幕不能再迁入事项。新事项请上传独立事件。
- 页面与列表 API 面向同一工作区用户，可浏览各事项；运行中的模型只收到自己任务和所属事项的上下文。这不是多租户账号体系。

## Party 业务行为

Party 状态包括参与人及状态、时间、地点、固定总价、人均预算和责任人。参与人退出保留历史身份；职责保留原负责人，并产生待重新分配提示。

人数、均摊费用、预算超支、责任缺口由 Python 规则计算。金额用整数分保存，均摊使用 Decimal，结果是四舍五入到分的估算，不是最终结算账单。模糊表态设为 `tentative`，显示确定参加者和全部待定者参加时的费用。无人确定参加时不计算均摊。

派生卡片字段 `editable=false`，禁止直接改人数或费用造成记忆不一致。通过用户补充重新生成，例如“蛋糕负责人：小王”。引用可以指向屏幕、该事项的历史记忆或用户补充；引用存在不代表模型语义正确，仍需核对。

默认 mock 仅支持演示约定的文本：

| 输入 | 行为 |
| --- | --- |
| `参加成员：小林、小王` | 初始化参与者，姓名用顿号分隔 |
| `聚会名称：…` / `时间：…` / `地点：…` | 更新基础信息 |
| `套餐总价：688元` / `人均预算：150元` | 更新金额（最多两位小数） |
| `蛋糕负责人：小林` | 指定已存在的成员负责该事项 |
| speaker=小林 + `我今晚不去了` / `我不来了` | 确认退出 |
| speaker=小林 + `我可能来不了` | 待确认 |
| speaker=小林 + `我又能来了` | 恢复参加 |
| 用户补充 `小林：退出` / `小林：待确认` / `小林：参加` | 修订成员状态 |

初始任务 instruction 用于表达处理目的；mock 的实际状态变化只来自上述屏幕格式和 revise.message。多条补充用换行分开。已处理的屏幕引用记入该事项，后续 mock 不重复应用旧消息。无法识别的文本或成员会明确失败；自由语义、多轮否定、冲突消息的准确理解需接入真实模型再验证。当前 mock 不支持新增/删除成员和复杂费用模型。
