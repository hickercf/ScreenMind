# Qwen 向量检索本机实测与产品接入决策

日期：2026-11-11。结论：真实 Qwen 权重已在本机离线运行。当前合成集合中，向量检索比现有词法检索更容易找回改写问题需要的证据；但现有非量化加载方式明显超出 2 GB 云服务器容量。本轮只新增实验脚本、样例、测试和报告，未修改线上配置或 APP。

## 1. 固定模型和测试环境

- 模型：[Qwen/Qwen3-Embedding-0.6B 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)，revision `97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`。
- 权重：1,191,586,416 字节（约 1.19 GB / 1.11 GiB），从官方 Hugging Face 仓库下载。
- 权重 SHA-256：`0437e45c94563b09e13cb7a64478fc406947a93cb34a7e05870fc8dcd48e23fd`，下载后与官方元数据核对一致。
- 电脑：Intel Core Ultra 5 125H，14核/18逻辑处理器，系统可见内存约15.52 GiB，Windows；本轮使用 CPU、4 个 PyTorch 计算线程、1 个 inter-op 线程。
- 实际加载精度：`torch.float32`。权重文件中的原始精度不能直接用来推断模型进程内存。
- 依赖：PyTorch 2.15.0+cpu、Transformers 4.57.1、Sentence Transformers 5.1.1、NumPy 2.2.6。
- 使用产品现有 `QwenEmbedding`，1024维、L2归一化、4096 token 上限；文档分批4条编码，查询逐条编码。查询使用现有英文任务前缀，文档无前缀，符合官方“查询带指令、文档直接编码”的用法。
- 加载后设为离线运行。无云端 LLM 调用、无模型训练、无生成答案评测。

## 2. 公平比较范围

数据文件：`examples/retrieval-comparison-v1.json`。

SHA-256：`be880194f9ae913841f2e0cdcb6aa8f87bbc4f864619fbbffd2663bc74b2f07d`。

共83条材料：44条 Party / Schedule / Trip 业务材料，36条干扰材料，3条其他事项/用户的相似材料。32个有答案问题覆盖原词、改写、条件与否定、OCR错字、编号和多证据问题；另有4个无答案诊断问题。题目及标签在查看 Qwen 排名之前固定，未根据结果改题或调参。

所有方法先按 owner/work 过滤，再对同一批原文排序。其他用户/事项材料不进入候选；这证明的是过滤逻辑有效，不是模型自己理解权限。每个查询实际有24或28个候选。

方法：

1. **现有词法**：直接调用产品 `lexical_scores`，中文单字/双字与英文数字词元，带 IDF 和长度归一化；不是通用中文检索的最强基线，也不是完整标准 BM25。
2. **Qwen 向量**：真实模型编码，归一化向量的点积作为余弦相似度，精确搜索。
3. **等权融合**：复用产品排序机制的两路 RRF，分别取前12条，`1/(60+rank)` 相加。raw 提取器没有额外实体通道。

不加入最近历史补充，不调用主 Agent；因此测到的是检索排序，避免“历史本来就全放进上下文”掩盖差异。分数相同按 source ID 排序以保证复现；线上同分时的输入顺序可能不同。本轮没有运行 LanceDB 存储或完整 MemoryService 上下文组装基准。

32题中共有35组必需证据；少数问题允许两个表达同一事实的来源任选其一。报告区分证据组召回率与“所有必需证据都找到的问题数”。

## 3. 检索效果

| 方法 | 前3条找齐证据的问题数 | 前5条找齐 | 前8条找齐 | 证据组召回@3 | 首条相关结果 MRR |
|---|---:|---:|---:|---:|---:|
| 现有词法 | 26/32 | 30/32 | 30/32 | 77.14% | 0.7807 |
| Qwen 向量 | 32/32 | 32/32 | 32/32 | 100% | 0.9688 |
| 等权 RRF 融合 | 30/32 | 30/32 | 32/32 | 94.29% | 0.8854 |

这些是小规模、作者编写的合成检索样例，不是独立人工标注的真实用户测试集。32/32不代表产品100%准确率，也不是 MTEB / LoCoMo 论文指标复现。只测了两道 OCR 错字题，不能据此宣称对广泛 OCR 噪声鲁棒。

具体差异：

- “生日甜点原先由谁准备？他退出后谁接手？”：Qwen 把“负责买蛋糕”和“确认退出且未交接”排在第1、2位；词法前8条仍未找齐。当前中文单字匹配容易被“准备、负责”等泛用词干扰。
- “为什么换了开会地点？”：Qwen 首位找到“投影仪损坏，所以换会议室”；词法前8条没有这一条。等权融合又把它降到第6位。
- “谁有必须避开的致敏食材？”：Qwen 首位找到花生过敏信息；词法排第4位。

不能假定融合总会优于单一路径。本轮不根据同一组测试结果调整权重再宣称提升；融合权重或按编号/语义路由，应使用另一组开发集选择，再在独立测试集验收。

## 4. 延迟与内存

两种方法分别运行在独立进程中。每个查询重复3轮，共108次计时；这是36道题的重复计时，不是108道独立质量样例。Qwen 先完成建库和一次查询预热，再计时；查询耗时包含 query 编码和相似度排序。词法耗时包含词元提取和打分。

| 指标 | 词法 | Qwen | 等权融合 |
|---|---:|---:|---:|
| 查询中位数 | 0.319 ms | 198.633 ms | 199.120 ms |
| 查询 P95 | 0.742 ms | 353.858 ms | 354.441 ms |
| 进程峰值常驻内存 | 30.49 MiB | 3.73 GiB | 与 Qwen 同进程，未单独测量 |
| 进程峰值提交量 | 16.71 MiB | 5.02 GiB | 与 Qwen 同进程，未单独测量 |

- 进程内首次加载（含框架导入）：94.11秒。没有清空操作系统文件缓存，不能称为标准冷盘加载基准。
- 83条文档向量构建：11.33秒，默认非量化 CPU；没有批量查询吞吐量或并发测试。
- 83条向量的原始 float32 数组：339,968字节，约332 KiB，不包含数据库元数据。主要内存成本在模型和运行时，不在这批向量。
- 查询结束时进程常驻内存约2.70 GiB，私有提交量约4.05 GiB；峰值主要出现在加载过程。
- 内存使用 Windows `GetProcessMemoryInfo`：WorkingSet / PeakWorkingSet 为常驻量，PrivateUsage 为当前私有提交量，PeakPagefileUsage 为峰值提交量。提交量可以由物理内存和页面文件支持，不能全部当作物理 RAM。结果包含 Python、依赖库、模型、工作缓存，不是模型权重独占量。
- 监控间隔50ms，并记录系统提供的进程峰值。开始时系统可用内存约2.84 GiB，最低采样值约5 MiB；本机其他程序同时运行，存在明显内存压力，所以加载及延迟可能受分页/缓存竞争影响。单机实测不能直接外推到 Ubuntu 2核服务器。
- 测试进程已退出，未留下常驻模型服务。

## 5. 无答案与隔离

4个无答案诊断问题均产生了向量近邻，这是 top-k 检索的正常行为，不表示找到答案。例如“接送司机手机号码”命中“司机联系人尚未确定”，相似度约0.585；“会议视频密码”命中不包含密码的会议室材料，相似度约0.448。

因此不能把余弦分数直接当作答案置信度，也不能仅凭相似就写入正式状态。本轮没有训练或校准拒答阈值。产品仍需回查原文、检验它能否支持回答、缺失时明确说明，并继续执行用户确认流程。检索出的旧消息也不能覆盖已确认的最新状态。

## 6. 产品接入决策

1. **现有2核2GB云服务器继续使用词法记忆检索。** 当前 float32 Qwen 运行方式超出容量；不在这轮将其打开，也不将电脑变成必须在线的生产依赖。
2. **保留 Qwen 作为下一阶段的语义检索选项。** 当前结果说明它对本产品的中文改写问题有潜在价值。先用独立、更多真实噪声的测试集验证，包括强中文词法基线、无答案、反复变更和长历史。
3. **接入形态采用一个共享的向量推理服务/实例。** 当前 `AgentHub` 为每个用户创建应用，而每个应用可各自构建 `QwenEmbedding`；直接开启会重复加载模型。下一阶段必须将模型生命周期从用户工作区中移出。用户/事项索引仍隔离，推理服务只做文本编码，不持有正式业务状态。
4. **运行策略：异步编码新增材料，查询只编码问题；超时或服务不可用时回退词法。** 初期可在独立测试环境试运行，不把未经验证的融合排序替换上线。正式发布前校验完整 MemoryService 来源回查、删除失效、版本隔离和用户交互。
5. **量化或远程 embedding API 是待验证方案。** 本轮没有测量 INT8/ONNX/BF16，也没有核实任何外部 API 的价格或数据处理条款；不能假设量化后一定能在2GB内稳定运行。若选外部服务，另行确认材料传输边界。

在 `Cloud Agent` 目录执行，确保已安装可选 qwen 依赖及已校验本地权重：

```powershell
.\.venv\Scripts\python.exe scripts/benchmark-retrieval.py --variant lexical
.\.venv\Scripts\python.exe scripts/benchmark-retrieval.py --variant qwen
.\.venv\Scripts\python.exe scripts/summarize-retrieval-benchmark.py
.\.venv\Scripts\python.exe -m pytest -q tests/test_retrieval_benchmark.py
```

汇总脚本还读取 `hardware.json`（CPU名称、物理/逻辑核心数），可通过 `Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors | ConvertTo-Json` 保存到结果目录。本轮保留了模型版本、数据集及原始结果文件的哈希，以便检查实验是否一致。
