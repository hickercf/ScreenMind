## 首段本地实现

网关环境变量 `SCREENMIND_AMAP_WEB_KEY` 用于启用高德 Web 服务调用。第一轮提供北京、上海、广州、深圳、杭州和成都的手选入口，天气使用行政区编码。确认日程地点和估算步行都由用户操作触发，选地点的搜索城市可独立于首页天气城市。当前采用步行模式和 5 分钟缓冲，作为首轮规则。路线估算针对查询当时，可用于判断计划是否宽裕。[高德天气](https://lbs.amap.com/api/webservice/guide/api/weatherinfo) · [高德地点搜索](https://lbs.amap.com/api/webservice/guide/api/newpoisearch) · [高德步行路线](https://lbs.amap.com/api/webservice/guide/api/newroute)

| 接口 | 本次约定 |
| --- | --- |
| `GET /api/v1/home/timeline` | 真实账号快照新增 `homeContext`，包含可选城市、天气、已核对地点和同日相邻日程的步行状态。保留 `weatherSummary` 和 `nativeState` 兼容 |
| `PUT /api/v1/home/context/city` | 传 `cityCode`，保存当前账号选的城市，尝试取得天气 |
| `POST /api/v1/home/context/weather/refresh` | 读取账号选定城市后刷新，App 可在数据到期时调用 |
| `GET /api/v1/places/search` | 传 `cityCode` 和 `query`，返回名称、地址、地点 ID，供用户区分同名地点 |
| `PUT /api/v1/events/{eventId}/place` 与 `DELETE /api/v1/events/{eventId}/place` | 使用 `placeId` 选中真实候选，或清除已选地点。按当前账号和事件校验 |
| `POST /api/v1/home/commutes/refresh` | 传 `date`、`fromEventId`、`toEventId`，校验相邻顺序。提供步行分钟、缓冲、距离、估算时间和剩余分钟 |

首页和 SSE 使用已取得的结果。天气和路线按时效短期复用，临时失败会保留原有时间轴并显示可重试的状态。天气查询失败后保持该状态，由用户主动刷新重试。缺少时间或地点时，首页按已知安排显示。未配置供应商密钥时仍可选城市，天气和步行数据会显示暂不可用。本轮已用替身响应完成本地联调，供应商实际返回、覆盖范围和账号权限待实测。附近推荐与报价沿用后续交付顺序。

## 建议的交付顺序

### 先做城市天气、地点确认和通勤

1. **用手选城市点亮天气。** 第一套联调地区按逻辑图使用中国大陆样例城市，例如上海。用户未授予位置权限时仍可选城市看天气。当前 Android 只有大致位置权限，附近搜索可使用粗略位置或选定地点。通勤估算优先使用用户已核对的日程地点或入口。
2. **先确认两端位置，再估算耗时。** 地点保留稳定标识、名称、地址、城市和供应商坐标系。遇到同名地点让用户选择。结果要带出行方式、预计时长、距离、查询时间和适用时段。只有当前路线估算时，界面可写「按当前路线估算」，未来时段交通依据仍需供应商能力。
3. **保留时间冲突的区别。** 事件重叠由起止时间确定。预计赶不上下一项则比较「下项开始 − 本项结束」与「路程耗时 + 缓冲」。缺少结束时间或目的地时显示「通勤时间待确认」，起止时间仍然可查。用户主动顺延后沿用第一批的同一事件 ID 和写回。

### 再做附近推荐和采纳

- 围绕已知目的地、两项日程间的路线，或用户当次选定的起点，搜索书店、公园、展览等地点。候选提供地点、预计路程和停留时长。营业时间有来源时才参与可行性判断，未知时显示「营业时间待确认」。
- 空档候选满足「去该地点耗时 + 停留 + 去下一站耗时 + 缓冲 ≤ 可用空档」。若缺少下一站参考或候选塞不进去，可以只保留「添加安排」。雨天的室内建议依据天气和地点类型生成。
- 采纳使用后端稳定的 `suggestionId` 或 `planId`，并核对账号、日期、前后两项的版本和候选有效期。候选失效提示「日程已变更，重新查看推荐」。成功后写入一条安排和准确的起止时间，重试返回同一张卡。

### 报价和履约按数据可用性推进

- 先接**只读报价**。同一候选要有 `offerId`、供应商、班次或商品标识、金额与币种、核价时间、可售状态，以及有效期或复核标记。现有预算筛选仍适用于已取回的候选。点击购买入口前刷新价格及可用性，首轮可跳转到已授权的官方渠道。
- App 内确认安排、供应商受理订单、实际出票或预约成功各有自己的状态。等团队取得相应地区和品类的生产权限、核价、查单、取消和回执能力，再接应用内履约。订单请求带幂等标识，最终状态由可查证的供应商回执更新。第三方票码仅在确实收到可展示的凭证时下发。
- 航班和铁路报价分别验证实际航线或车次覆盖。Amadeus 官方订票文档展示了搜索、核价、下单和查单的顺序，并列出了生产出票的合作条件。它可作为流程例证，中国大陆航线覆盖和团队接入资格需要独立核对。[Amadeus 官方订票说明](https://admin.developers.amadeus.com/self-service/apis-docs/guides/developer-guides/faq/)

## 现有接口怎么承接

下表中的新增字段和接口是提议，命名在供应商试接后确认。

| 用途 | 可复用入口 | 需要补齐 |
| --- | --- | --- |
| 天气与来源 | `GET /api/v1/home/timeline` | 可选 `ambientHeader.weather`，含城市标识、状况、温度、发布时间和数据状态。保留现有 `weatherSummary` 供旧版使用 |
| 查找地点 | 建议新增 `GET /api/v1/places/search` | 支持关键词、城市标识。返回可选择的地点 ID、名称和地址。保留供应商和地点 ID，用于路径估算并区分同名地点 |
| 通勤提示 | `GET /api/v1/home/timeline` 的 `connectorToNext` | 按前后事件 ID 保存 `gapMinutes`、交通方式、预计时长、缓冲、估算时间和状态。旧客户端仍可用中文标签显示 |
| 查找附近方案 | `POST /api/v1/home/explore/refresh` | 复用日期和排除已看方案，按需提供选定地点或当次大致位置，也可带空档两端的事件 ID。返回带时效的候选和各路段耗时 |
| 采纳或顺延 | `POST /api/v1/home/actions/execute` | 沿用 `ADOPT_GAP_SPOT`、`ADOPT_EXPLORE_PLAN`、`SHIFT_EVENT_TIME`，按候选 ID 校验。保留此前的本地演示请求兼容 |
| 方案和报价 | `GET /api/v1/events/{eventId}/detail` | 有真实报价后在方案模块提供来源和有效性，核价流程单独触发。现有 `confirm` 继续表达确认本次安排 |
| 更新到手机 | `GET /api/v1/home/stream` | 外部数据更新成功后仍用现有事件流通知客户端。Android 的日常首页还需要读取实际的天气、候选和通勤数据，光补接口返回不会让页面出现新内容 |

天气、地点和路线由网关调用上游。天气查询只需城市，路线与附近查询按场景传所需地点或当次位置。读首页及重连用已经取得的结果；地点或安排变化、用户点刷新、以及数据到期时再按策略查询。相同结果可在供应商许可范围内合并请求和短时复用。天气保留发布时间，路线保留估算时间。慢请求或供应商异常时，日程和详情仍可打开。天气过期可标注上次更新时间，路线过期后按「通勤时间待确认」显示，报价过期后引导刷新。真实账号的缺失数据使用空态和中文反馈；演示样例继续从演示入口访问。

## 供应商候选与验收

**大陆样例的第一候选是高德。** 官方接口支持通过行政区编码查天气，也提供地点搜索、步行和其他交通方式的路径估算，以及坐标转换。前端可先展示地点地址、距离和预计分钟数，通过地图入口查看导航。若需要逐小时天气或可查询的天气预警，再评估和风天气的当前接口。上线范围由目标城市实测覆盖、团队账号权限、调用配额和数据使用条件决定。[高德天气](https://lbs.amap.com/api/webservice/guide/api/weatherinfo) · [高德地点搜索](https://lbs.amap.com/api/webservice/guide/api/newpoisearch) · [高德路线规划](https://lbs.amap.com/api/webservice/guide/api/newroute) · [高德坐标转换](https://lbs.amap.com/api/webservice/guide/api/convert) · [和风天气](https://dev.qweather.com/docs/api/weather/) · [和风天气预警](https://dev.qweather.com/docs/api/warning/weather-alert/)

**首个可验收场景。** 用户手选城市，在当日两项带明确地点的日程间看到真实通勤估算。打开空档，至少一个真实候选显示停留时间和到下一站的路程。采纳后，手机首页、卡片详情和桌面控制台读到同一个事项和时间。

| 验收条件 | 预期 |
| --- | --- |
| 拒绝定位、选定城市 | 天气仍然能用，附近候选使用用户主动选定的地点 |
| 门店同名、地点缺失、查路线超时 | 提示选地点或暂缺估算，原日程和本地时间冲突继续可读 |
| 路程与停留超出空档、地点明确已关门 | 候选不可采纳，保留原来的时间轴 |
| 刷新后候选已变或协作设备修改了日程 | 旧方案要求刷新；同一次采纳重试只产生一张卡 |
| 上游没有报价或可核验证明 | 暂缺报价或凭证，用户可使用有来源的已有安排 |
| 多次刷新首页、断线重连 | 手机和桌面显示同一版本，读快照时的上游调用次数与重连次数解耦 |

静态分析依据本地代码和供应商公开文档。真实天气、路线、报价和交易结果的验收仍需团队测试账号和对应数据服务。
